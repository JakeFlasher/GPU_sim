## Lesson: fit-input-validation-split
Lesson ID: BL-20260526-fit-input-validation-split
Scope: scripts/baselines_harness/metrics/isotonic_calibrator.py + calibration/cache_prediction/ sidecar persistence
Problem Description: Refitting `IsotonicCalibrator` on a ledger that contains both calibration_only and validation_only slugs silently admits validation-only rows to the fit when `validation_split` is not passed; the persisted sidecar's `fit_record_count` then exceeds the calibration_only count, and the held-out validation set has been seen during fit.
Root Cause: `IsotonicCalibrator.fit()` only enforces the split contract when `validation_split` is supplied. The default `validation_split=None` silently admits everything.
Solution: Always pass `validation_split=split_map` into `IsotonicCalibrator.fit(...)` when persisting params to a sidecar AND pre-filter records to `[r for r in records if split_map.get(r.cell_name) == "calibration_only"]` before the call. Add a regression test that `params.fit_record_count == len(calibration_only_slugs)`.
Constraints: Applies to all sidecar fits across arches (sm_86 today only via the fit-at-runtime path; sm_120 + future arches via sidecars). In-memory smoke fits in test fixtures may legitimately skip the contract for synthetic single-fold patterns.
Validation Evidence: `scripts/baselines_harness/tests/test_sm120_calibrator_loader.py::test_load_sm120_matches_in_memory_refit_within_1e_12` (commit 33cab662) plus `isotonic_params_sm120.toml::fit_record_count = 12 == len(calibration_only_slugs)`.
Source Rounds: 0 (bug introduced), 1 (fixed + bitlesson recorded)

## Lesson: canonical-bucket-source-of-truth
Lesson ID: BL-20260526-canonical-bucket-source-of-truth
Scope: scripts/baselines_harness/metrics/isotonic_calibrator.py + any ledger-driven calibrator fit / refit / roundtrip code
Problem Description: A calibrator fit/refit driven by reading the ledger's `predictor_bucket` field for each entry fails with `calibration_input_invalid` because the ledger's per-cell bucket can disagree with the canonical partition in `predictor_design_coverage.py`. The calibrator validates the record's bucket against `lookup_predictor_design_coverage(cell_name).predictor_bucket` and refuses any disagreement.
Root Cause: Ledger bucket assignments are operator/harvest-side decisions; the canonical partition in `predictor_design_coverage.py` is the load-bearing single source of truth the calibrator enforces. Older ledgers + post-hoc cohort classifications can drift from the canonical partition.
Solution: When building `CalibrationInputRecord`s for fit/refit, ALWAYS call `lookup_predictor_design_coverage(cell_name)` and use `canonical.predictor_bucket` (not the ledger's `predictor_bucket`). Skip cells the lookup rejects (`PredictorDesignCoverageError`) or the canonical bucket is `PREDICTOR_BUCKET_TYPED_UNAVAILABLE`.
Constraints: Applies to refit code that reads ledger entries. New tests that synthesize CalibrationInputRecord without going through the ledger should still respect the canonical mapping.
Validation Evidence: `scripts/baselines_harness/tests/test_sm120_calibrator_loader.py::test_load_sm120_matches_in_memory_refit_within_1e_12` + `test_sm120_calibrator_roundtrip.py::test_l1_head_roundtrip_matches_refit` (both regressed and were fixed in Round 2 by switching refit helpers to use the canonical bucket).
Source Rounds: 2 (bug observed when cohort_b ledger entries diverged from canonical partition; fixed same round)

## Lesson: identity-fit-smokescreen
Lesson ID: BL-20260526-identity-fit-smokescreen
Scope: Any persisted calibrator sidecar that maps raw predictor predictions to ground-truth labels
Problem Description: When building `CalibrationInputRecord` objects from a ledger that carries only NCU labels (no separate simulator raw output), it is tempting to set `raw_l*_prediction = ncu_l*_label` as a proxy. The resulting calibrator is an IDENTITY fit (x_thresholds == y_thresholds), validates trivially with near-zero residuals, but does not actually validate predictor accuracy. Symptom: `all_gates_pass = true` with all residuals == 0.0; the persisted sidecar's anchor pairs show `x_threshold == y_threshold` at every position.
Root Cause: The calibrator's contract distinguishes "what the predictor would output (raw)" from "what NCU measured (label)". Conflating them collapses the calibrator's domain and makes the fit meaningless.
Solution: Either (a) produce REAL simulator raw output for each cell (NVBit traces → set_associative_simulator → predict_from_launch_frame) and pair with NCU labels, or (b) when simulator output is not constructible (e.g., geometry unresolved per DEC-B), mark cells `predictor_typed_unavailable` with a typed reason tied to the structural blocker. NEVER ship a calibrator whose anchor pairs are identity-only.
Constraints: Applies to every per-arch sidecar (`isotonic_params_<arch>.toml`). A reviewer can spot the failure mode by checking the persisted x_thresholds and y_thresholds: if they are identical at every position, the fit is identity.
Validation Evidence: `scripts/baselines_harness/calibration/cache_prediction/sm120_validation_report_v1.toml` in Round 3 (`all_gates_pass = false`, `fail_closed_reason = "calibrator_typed_unavailable_due_to_sm120_l2_geometry_unverified"`) — the corrected fail-closed state. Commit ad93ea0f.
Source Rounds: 1 (introduced), 2 (entrenched + flagged by Codex), 3 (acknowledged + fixed via ledger-side typed-unavailable path)

## Lesson: typed-unavailable-sidecar-propagation
Lesson ID: BL-20260526-typed-unavailable-sidecar-propagation
Scope: scripts/baselines_harness/metrics/cache_predictor.py loader + compose_predictor_bundle
Problem Description: When a calibrator sidecar reports `meta.calibrator_status = "typed_unavailable"` (e.g., sm_120 with DEC-B-pending geometry), a naive loader returning bare `None` makes `compose_predictor_bundle` fall back to the generic `coverage_below_smoke_floor` reason. Move full schema validation (`_validate_sidecar_meta`) BEFORE the typed-unavailable short-circuit so arch / metric-family / reproducibility / hash gates still fire.
Constraints: Backwards compat: legacy sm_86 empty-string sidecar entries still return `None` (no change). Only typed-unavailable sidecars route through the new marker.
Validation Evidence: `scripts/baselines_harness/tests/test_compose_arch_keyed_dispatch.py::test_sidecar_typed_reason_propagates_into_bundle_reasons` asserts `bundle.arm_payload.typed_reason == "sm120_l2_geometry_unverified"`. Commit 9900b676.

## Lesson: artifact-self-consistency-qa
Lesson ID: BL-20260526-artifact-self-consistency-qa
Scope: scripts/baselines_harness/calibration/cache_prediction/*.toml + scripts/baselines_harness/tests/test_sm120_artifact_consistency.py + any future signed-artifact pipeline
Problem Description: A pipeline that stamps cross-artifact SHA-256 hashes + entry counts (e.g., ledger SHA stamped in sidecar; sidecar SHA stamped in validation report; ledger entry count stamped in both sidecar denied-cell list and validation report) accumulates silent drift the moment any one file is hand-edited without refreshing the downstream stamps. Symptom: the committed file's `meta.ledger_sha256` no longer matches `sha256(ledger.toml)`; a planted-mutation in the ledger silently passes because the loader doesn't recompute the live hash by default; the split file claims N measured cells while the ledger has 0.
Root Cause: (1) Cross-stamps are normally written by an emit-once script and have no self-validation gate. (2) The loader's `expected_*_sha256` parameters default to `None`, making the live-hash check opt-in rather than fail-closed. (3) No test compares the artifact's own stamps to a recomputation of the underlying files. (4) Generators that produce one artifact don't always know the entry count of a sibling artifact they depend on, so the cross-count drifts as the other artifact regenerates.
Solution: Land a dedicated artifact-consistency QA test module that recomputes every cross-stamp from disk and asserts byte equality. Pair it with a default-on live-hash check in the runtime loader (no caller-supplied `expected_*_sha256` should be required for the fail-closed behavior). Ship planted-mutation negatives so the gate's own behavior is tested. For count cross-stamps, do the same: recompute the entry count from the underlying artifact and assert the stamped count matches. Tests must live next to the artifacts; the gate must fire automatically in the sweep, not require operator vigilance. Factor the consistency check into a reusable helper (e.g. `assert_artifact_stamps_match_disk(...)`); planted-mutation tests must invoke the helper and assert it raises, not just compare `stamped != live` — `stamped != live` arithmetic only proves the mutation diverges, not that any QA code path actually fires. Additionally, when the default-on live-hash check resolves the live file from a dispatch table, the missing-file corner MUST fail closed via a dedicated typed reason (e.g. `calibrator_live_artifact_missing`); `if path.exists(): recompute` silently degrades to opt-in validation. Also assert slug-set IDENTITY between artifacts that share a population (not just count equality) — equal counts can mask divergent slugs.
Constraints: Applies to any signed-artifact pipeline (calibrator sidecar + validation report + ledger + split + sibling-split). Does NOT replace artifact regeneration scripts; it just catches drift after the fact. When refactoring split semantics across rounds, both the artifact files AND the QA test must move in lockstep so a count-zero (fail-closed empty) state is recognized. CROSS-ARCH GOTCHA: a cross-stamp can live in a SIBLING arch's immutability fixture (e.g. an sm_86 calibration file SHA-pinned inside the sm_120 immutability fixture, because the fixture locks the whole `calibration_cache_prediction` category, not just sm_120 files). A per-arch "refresh audit hashes" commit that regenerates one artifact MUST re-run the FULL cross-arch immutability sweep (`pytest test_sm120_artifacts_immutable_v1.py test_baseline_artifacts_immutability.py`), or it silently leaves the sibling fixture stale and the RED only surfaces on the next full sweep.
Validation Evidence: `scripts/baselines_harness/tests/test_sm120_artifact_consistency.py` (22 tests, including 4 helper-based planted negatives and a slug-set identity check) + `scripts/baselines_harness/tests/test_sm120_calibrator_loader.py::test_default_on_live_ledger_hash_check_catches_stale_sidecar`, `..::test_default_on_live_split_hash_check_catches_stale_split`, `..::test_missing_live_ledger_with_no_caller_hash_raises`, `..::test_missing_live_split_with_no_caller_hash_raises`. Round 5 landed the default-on hash check + dispatch tables; Round 6 closed the missing-live-artifact corner + refactored planted negatives to exercise the QA path. sm86-coverage-loop R0: caught + fixed a concrete instance — `sm120_artifacts_immutability_v1.json` carried a stale SHA (`2a6784…c7fffb…`) for `sm86_baseline_predictions_v1.toml` because R24 (`31a687d8` "refresh audit hashes") regenerated the file (→`ea9eb8…`) without refreshing this sibling-arch cross-stamp; 2 tests had been RED on clean HEAD since R24.
Source Rounds: 4 (drift introduced by hand-edit between rounds), 5 (resolved via artifact consistency QA + default-on hash check), 6 (closed the missing-artifact corner + strengthened planted-negative methodology), sm86-coverage-loop R0 (concrete sibling-arch cross-stamp drift caught + fixed; added the cross-arch full-sweep constraint)

## Lesson: empirical-geometry-sweep-with-trace-replay
Lesson ID: BL-20260526-empirical-geometry-sweep-with-trace-replay
Scope: scripts/baselines_harness/calibration/cache_prediction/sm120_l2_associativity_probe/ + any future arch where a cache-geometry field (associativity, line size, set count) is undocumented by NVIDIA and not exposed by NCU device-query
Problem Description: For new GPU architectures with undocumented cache geometry, the static-card field may end up `None` and force the predictor into typed-unavailable. The simulator's set-count consistency invariant `(l2_capacity_bytes // num_l2_slices) % (line_size_bytes * associativity_l2) == 0` requires both `num_l2_slices` AND `associativity_l2` to be resolved. When NCU exposes one (e.g., `device__attribute_l2s_count`) but not the other (`associativity_l2` has no device-attribute), the architectural blocker is permanent unless an empirical method is used. Naive cache-conflict microbenchmarks defeated by NVIDIA's L2 slice-mapping hash, so direct conflict-cliff probing doesn't yield clean signal (three probe variants on GB206 sm_120 flatlined at ~70-90% baseline).
Root Cause: Cache associativity is a fixed hardware property NVIDIA does not always publish for consumer parts. Live-device probing via stride-sweep cache-conflict probes (the classical Saavedra technique) is defeated by the L2 slice-mapping hash because the hash spreads accesses across slices, denying any naive stride pattern access to a single slice's set. Per-arch reverse-engineering of the hash is a research project.
Solution: Use a calibration-driven empirical SWEEP rather than direct hardware probing. (1) Re-harvest per-cell Tier-2 NVBit address traces for the calibration set; (2) for each candidate `associativity_l2` ∈ {power-of-2 set; e.g., 4, 8, 16, 32, 64}, drive the set-associative simulator on the traces to produce raw L1/L2 predictions; (3) fit the isotonic calibrator on the calibration_only cells; (4) evaluate per-cohort MAPE on validation_only cells; (5) select the candidate that minimizes per-cohort MAPE under the gates. Three caveats: (a) the simulator's set-count check needs a clean per-slice byte count — round the physical L2 capacity to a divisor-friendly value (e.g., 32 MiB physical → 30 MiB simulator-effective with 24 slices × 1280 KiB each, divisible by every power-of-2 associativity in the sweep); (b) NVBit's compile-time `TIER2_RECORDS_PER_LAUNCH=524288` cap forces an offline-calibration truncation-relaxation — strip the truncation marker after parse, record it as provenance, document explicitly; (c) per-cell Tier-2 byte budget defaults are too small for cohort_b GEMM/attention cells — default the orchestrator to 256 MiB per slot.
Constraints: The result is empirical model-selection, NOT authoritative hardware geometry. Provenance MUST explicitly say "empirical_sweep" not "NVIDIA-sourced fact". Operator concurrence required before relying on the swept value for AC-5 gate evaluation. The set of candidates should be a closed vocabulary committed in code; ad-hoc sweeping invites cherry-picking. Per-cohort calibrators are NOT supported under the current single-head sidecar schema; the sweep evaluates a combined fit and reports per-cohort MAPE independently (matching the operator's tiered-gates contract).
Validation Evidence: `scripts/baselines_harness/calibration/cache_prediction/sm120_l2_associativity_probe/{harvest_tier2_traces,sweep_associativity,persist_fitted_sidecar}.py`; Round 10 picked `associativity_l2=32` for sm_120/GB206 with friendly L2 MAPE plateau at 0.0726 (32) vs 0.1608 (16), 0.2141 (8); assoc=64 yields identical numbers to 32 (saturation confirms 32 as the regime boundary).
Source Rounds: 10 (DEC-B's second variable resolved via this pattern after three direct-probe variants failed)

## Lesson: geometry-flag-alone-without-submodel-regresses
Lesson ID: BL-20260527-geometry-flag-alone-without-submodel-regresses
Scope: scripts/baselines_harness/metrics/cache_geometry.py + cache_access_policy.py + cache_predictor.py (any geometry-driven flag that re-routes traffic between cache-hierarchy components)
Problem Description: When a cross-arch metric-family divergence (e.g., Ampere LSU-pipe `lts__t_sector_op_read_*` excludes constant-cache backstop traffic, whereas Blackwell-consumer / Hopper texture-source-unit semantics include it) tempts a "just thread the boolean through the geometry → policy → predictor stack" fix, the plumbing alone can make predictions strictly worse. Flipping the new `l2_constant_memory_counts_for_read_score` flag True for sm_120 routed constant-memory loads to the regular L2 LRU simulator. Because constant working sets are tiny (~few KiB) they collapse to ~98 % hit rate under LRU alias, while NCU's actual constant-cache hit rates for the same 3 ROPE / RMSNorm cells span 8–76 % with per-cell variance (0.22, 0.29, 0.53) that no monotonic isotonic correction can recover. Friendly L2 MAPE regressed from 0.0378 to 0.1187.
Root Cause: A geometry-driven flag only re-routes accesses between EXISTING simulator components. If the destination component does not faithfully model the cache structure the flag now sends traffic to (here: the regular L2 LRU simulator is the wrong substrate for the parallel constant cache's ~8 KiB capacity + broadcast semantics), the routing change amplifies the mis-model. The plumbing is necessary but not sufficient.
Solution: Land the plumbing in three stages, gate the activation on the submodel. (1) Stage 1 — geometry plumbing: thread the bool through `_STATIC_DEVICE_CARDS`, `_STATIC_DEVICE_CARD_PROVENANCE`, `resolve_cache_geometry` (with closed-vocabulary source labels `static_device_card` / `constant_default`), `route_access` (kwarg with safe default), and the predictor's `_replay_records_through_caches` (geometry-driven; no arch flow-control branches per AC-7). (2) Stage 2 — sm_86 byte-equality guard: the default-False value MUST preserve the historical arch's byte-equality at 1e-12 (DEC-C). (3) Stage 3 — opt-in activation: the FIRST arch whose flag flips True must have a dedicated submodel that models the routed-to cache structure faithfully. Until Stage 3 lands, the flag stays False with explicit provenance documenting why. Do not flip the flag with the regular L2 LRU as the routing target; the LRU-alias collapse is not recoverable by isotonic regression.
Constraints: Applies to any geometry-driven simulator flag, not just constant-cache. Whenever the routing change moves traffic between components with different replacement / capacity semantics (e.g., LRU vs FIFO, sectored vs full-line), verify the destination's modeling fidelity BEFORE flipping. Document the gating relationship in the provenance string and in any per-cell exclusion manifest that depends on the deferred submodel.
Validation Evidence: `scripts/baselines_harness/calibration/cache_prediction/sm120_simulator_unavailable_cells_v1.toml` (Round 11) documents the rollback decision and the queued Extension A2 dependency. Tests `test_sm_86_card_pins_l2_constant_memory_counts_for_read_score_false`, `test_sm_120_card_pins_l2_constant_memory_counts_for_read_score_false`, `test_resolver_defaults_l2_constant_memory_counts_when_card_silent` (cache_geometry); `test_constant_load_counts_for_l2_read_score_when_flag_true`, `test_constant_load_default_flag_false_preserves_sm86_behavior`, `test_constant_load_non_load_op_with_flag_true_still_fails_closed` (cache_access_policy). Commit `dfaad4d3`.
Source Rounds: 11b (introduced + rolled back + plumbing preserved); future Extension A2 will flip sm_120's flag True with no further plumbing changes.

## Lesson: simulator-out-of-domain-typed-exclusion-vs-model-fix
Lesson ID: BL-20260527-simulator-out-of-domain-typed-exclusion
Scope: scripts/baselines_harness/calibration/cache_prediction/sm120_simulator_unavailable_cells_v1.toml + any future per-arch simulator-OOD manifest
Problem Description: When a fitted calibrator's gate failures are NOT caused by calibrator fit / partition / split issues but by STRUCTURAL gaps in the underlying simulator (e.g., flat-stream LRU cannot model per-warp KV-cache reuse; regular L2 LRU cannot model the constant-cache's ~8 KiB broadcast structure), per-cohort MAPE will not converge below threshold no matter how the calibrator is refitted. The simulator is producing predictions outside its modeling capacity. Symptom: a small specific set of cells (here: 5 cells out of 65) shows per-cell residuals that are an order of magnitude larger than the rest, the residuals are systematic (raw=0 vs ncu=0.7, raw=0.04 vs ncu=0.86), and the isotonic regression's monotonicity prevents it from recovering ground truth.
Root Cause: Isotonic calibrators model a monotonic shift of the raw prediction. They cannot recover ground truth from a raw prediction that is on the wrong side of any non-monotonic relationship (e.g., constant-mem cells with per-cell variance 0.22 / 0.29 / 0.53 vs raw=0.98 LRU collapse). Refitting and reshuffling splits is rearranging deck chairs — the underlying simulator is missing the cache structure entirely.
Solution: Closed-vocabulary typed exclusion. Land a sibling TOML (`sm120_simulator_unavailable_cells_v1.toml`) with: schema_version, manifest_meta (host_arch, applies_to_split, applies_to_calibration_path, applies_to_validation_path, total_excluded), and an `[[excluded]]` array of `{cell_name, typed_reason, detail}` entries where `typed_reason` ∈ a closed vocabulary (here: `simulator_l2_metric_family_undercount`, `hostile_subclass_uncalibrated`). The exclusion routes the cell to `predictor_typed_unavailable` in the bundle with the typed reason — NOT silently dropped from the fit. Cross-stamp `simulator_unavailable_manifest_sha256` into the sidecar AND validation report, so a drift in any of the three files fires the QA path. The exclusion manifest is the structural blocker's persistent record; subsequent operator-driven plans (Extension A2 for constant-cache; Extension B for per-warp reuse) reference these typed reasons as their re-admission trigger.
Constraints: Use only when the simulator-correctness defect is precisely characterizable (named cells, named typed reason, named submodel that would re-admit). Do NOT use as a catch-all for "the gates don't pass and I don't know why". Operator concurrence required for the typed-reason vocabulary additions. Each `detail` paragraph must name the architectural assumption that fails (here: LSU-pipe source-unit semantics, parallel constant cache's ~8 KiB capacity, per-warp KV-cache reuse beyond flat-stream LRU). The number of excluded cells must be small relative to the validation set (here: 5 of 70 ≈ 7 %); a large exclusion footprint signals the calibrator domain is wrong, not just per-cell defects.
Validation Evidence: `sm120_validation_report_v1.toml` Round 11a: friendly L1=0.0357, L2=0.0378, hostile L1=0.0000, L2=0.0203 (`all_gates_pass=true`) with `simulator_unavailable_cells_count=5`. `sm120_simulator_unavailable_cells_v1.toml` carries the 5 excluded cells with typed reasons + per-cell `detail` strings naming Extension A2 / B as the re-admission triggers. Commit `5ca42d35`.
Source Rounds: 11a (introduced as the close-out mechanism for two simulator-correctness gate failures Codex Rounds 8 / 9 / 10 deferred until DEC-B closed).

## Lesson: match-reference-precision-profile-in-port
Lesson ID: BL-20260527-match-reference-precision-profile-in-port
Scope: baselines/<cat>/<slug>/cuda_cpp/ hand-ports whose upstream reference uses PyTorch `F.linear` / `F.conv*` / similar cuBLAS / cuDNN-backed ops + accumulates in FP32 + casts the input down to a smaller dtype between phases
Problem Description: A custom `__global__` kernel that keeps an intermediate value (e.g. RMSNorm's normalized vector) in FP32 throughout when the upstream PyTorch reference materialises it as FP16/BF16 before the next matmul will diverge from the reference for output values near zero by ~the FP16/BF16 quantisation step. sol-execbench's `required_matched_ratio=0.99` gate then fires on the smallest workload's tightest `atol` because > 1 % of near-zero output elements straddle the rounding boundary differently than the reference. The custom kernel is "more precise" than the reference yet fails the correctness gate.
Root Cause: PyTorch's reference `run(...)` body is the contract. Lines like `(norm_weight * hidden_states).to(input_dtype)` and `F.linear(normalized, weight)` quantise the intermediate down to the input dtype before the matmul. cuBLAS's matmul thus consumes FP16 inputs and accumulates in FP32, while a custom kernel that hands FP32 inputs to the same accumulator computes a strictly more precise result that drifts from the reference by the quantisation noise the reference itself swallowed.
Solution: Match the reference's intermediate dtype profile, not the most-precise version. Specifically: when storing an intermediate vector in shared memory for reuse across a matmul, cast it to the dtype the upstream reference would have materialised at that point (typically the input dtype) BEFORE the shared write. Read it back as the smaller dtype, promote to FP32 inside the per-thread accumulator. The matmul accumulator stays FP32 (correct); the inputs to the matmul match the reference's precision (correct gate behaviour). Side benefit: halves the shared-memory footprint (FP32 → FP16 → 2 KiB instead of 4 KiB at HIDDEN_SIZE=1024).
Constraints: Applies to forward-only ports whose PyTorch reference contains an explicit `.to(input_dtype)` cast between an intermediate computation and a matmul / conv that consumes it. Does NOT apply to ports whose reference keeps the intermediate in FP32 end-to-end (rare; check the spec). The cast site is whatever the reference does — `(weight * value).to(input_dtype)` for RMSNorm-then-linear; `F.relu(value).to(input_dtype)` for an activation-then-matmul; etc. The pattern is "match the reference's exact precision profile" not "always FP16-quantise the intermediate". **CONVERSE (R16, ATen-delegated ports): if the reference run() has NO `.to()` and operates in bf16 END-TO-END (every elementwise mul/add/cat/sum is bf16), the port MUST stay bf16 too — do NOT upcast inputs to fp32 "for numerical stability" and round once at the end. An all-fp32 compute chain is STRICTLY MORE precise than the bf16 reference, so accumulated per-op bf16 rounding diverges and >1% of elements straddle the rounding boundary → INCORRECT_NUMERICAL on EVERY workload (not just the smallest). This bites analytic-backward ATen ports especially, where the temptation to "upcast for stability" is strongest. Mirror the reference dtype verbatim; `at::sum` on bf16 already accumulates in fp32 internally (acc_type) so it matches torch.sum's bf16 path.**
Validation Evidence: `baselines/L1/problem_073_fused_encoder_final_norm_to_decoder_cross_attention_kv_projection/cuda_cpp/kernel.cu` (Round 20): before the fix, 15/16 workloads PASSED, 1 INCORRECT_NUMERICAL on the smallest workload's atol=2.9e-5 gate; after switching `s_normalized` from `__shared__ float[1024]` to `__shared__ __half[1024]` (with the cast applied before the shared write), 16/16 workloads PASSED. Same change pre-applied to `baselines/L1/problem_006_hyena_depthwise_conv1d_split_gate/cuda_cpp/` saved a debugging round. **CONVERSE evidence (sm86-coverage-loop R16): `baselines/L1/problem_062_kv_cache_update_with_rope_backward/cuda_cpp/main.cpp` — the ATen-delegated RoPE-backward, whose algebra matched the reference op-for-op, FAILED all 16 workloads INCORRECT_NUMERICAL when computed in fp32 (inputs `.to(kFloat32)`, results cast to bf16 at the end); removing the fp32 upcast and operating natively in bf16 (matching the reference, which has zero `.float()` calls) → 16/16 PASSED.**
Source Rounds: 19 (introduced + diagnosed: 15/16 workloads on problem_073), 20 (resolved + bitlesson recorded), sm86-coverage-loop R16 (CONVERSE direction: a bf16-native backward reference where fp32 upcast failed all 16; bf16-native passed).

## Lesson: repo-walker-stat-guards-non-regular-files
Lesson ID: BL-20260528-repo-walker-stat-guards-non-regular-files
Scope: Any test or scanner that walks the working tree (e.g. `os.walk`) and inspects files via `open(path, "rb")` — primarily `scripts/baselines_harness/tests/test_warm_cold_pinning_mirror_locations_complete.py::_is_binary_file` and any future whitelist walker that follows the same shape.
Problem Description: A repo walker that opens each candidate path in binary mode to sniff for null bytes will block indefinitely the instant it encounters a named pipe (FIFO) with no live writer. Concrete trigger seen in R7: 36 leftover NVIDIA-treetracker FIFOs lived under `.harness_traces/<bundle>/static/staging/NVIDIA-treetracker-*/pipe-*-ownerReadingStream` after prior `nsys` / NVBit runs; the producer end was long gone, so each `open(fifo_path, "rb")` blocked forever waiting for a writer. The full harness suite hung at the 95–96 % progress marker with `wait_for_partner` wchan on the parent — easy to mis-attribute to fork-in-multithreaded-process deadlock when the real cause is open-on-FIFO.
Root Cause: `open(path, "rb")` follows POSIX FIFO open semantics: when no `O_NONBLOCK` flag is given, opening for read blocks until a writer opens the other end. The bug is environmental — gitignored leftover instrumentation FIFOs are invisible to `git status` but very visible to `os.walk` — and recurs whenever an `nsys` / NVBit / treetracker run terminates abnormally.
Solution: Always `os.stat` the path first and check `S_ISREG` BEFORE opening. Treat non-regular files (FIFOs, sockets, character devices, symlinks-to-nowhere) as "skip-as-if-binary" — return early with the same skip semantics the walker uses for real binaries. Catch `OSError` on the stat itself for the same reason. The contract test must include a positive case that builds a real FIFO via `os.mkfifo` with no writer attached and asserts the helper returns immediately without blocking — a unit test that only checks `S_ISREG` against synthetic stat results can pass while leaving the live behavior broken.
Constraints: Applies to all repo walkers that read file contents, not just `_is_binary_file`. Operationally pair the code fix with a cleanup pass (`find . -type p -delete` against the artifact tree) so a fresh checkout starts clean; the stat-guard prevents future regressions but does not remove already-leaked FIFOs. Note that the AC-5 deadlock had two distinct sources — the FIFO-blocking walker AND fork-in-multithreaded-process with CUDA threads alive — fixing the spawn pin in `conftest.py` is necessary but NOT sufficient; both fixes coexist.
Validation Evidence: `scripts/baselines_harness/tests/test_walker_skips_non_regular_files.py` (4 tests: FIFO without blocking, UNIX socket without blocking, regular ELF still recognised as binary, regular text still recognised as text). Full-suite empirical: `pytest scripts/baselines_harness/tests/ --ignore=test_workspace_consolidation.py --timeout=120` returns exit code in 1:50 (3517 passed, 15 failed, 13 skipped) — no hang. Commit `4411d8d9`.
Source Rounds: R5 (introduced: pytest deadlock spans multiple sessions); R6 (mis-diagnosed as fork-only); R7 (re-diagnosed via `pytest --timeout --timeout-method=thread` + live `/proc/<pid>/wchan` probe → identified `_is_binary_file → open()` as the block point; FIFO-skip fix landed); R8 (bitlesson recorded).

## Lesson: delegate-matmul-to-at-matmul-for-reference-hgemm-precision-parity
Lesson ID: BL-20260528-delegate-matmul-to-at-matmul-for-reference-hgemm-precision-parity
Scope: baselines/<cat>/<slug>/cuda_cpp/ hand-ports whose reference uses PyTorch `F.linear` / `at::matmul` / similar cuBLAS-backed matmul on FP16 inputs, AND whose ground-truth dtype is FP16, AND that fail `sol-execbench` correctness tolerance on a single small-shape workload while passing every other workload. Cross-arch failure pattern: passes on the sm_120 RTX 5060 Laptop host but fails on the sm_86 RTX 3090 Ti host with `max_absolute_error ≈ 2^-9` and `matched_ratio < 0.99`. Related but distinct from [[match-reference-precision-profile-in-port]] which covers the intermediate-dtype-cast pattern; this lesson covers the *reduction*-precision divergence inside cuBLAS HGEMM.
Problem Description: A hand-written kernel that does the matmul step in a custom CUDA inner-product (FP16 inputs, FP32 accumulator, 4-way pairwise or serial reduction) will produce a strictly higher-precision result than PyTorch's `F.linear` because PyTorch's default `torch.backends.cuda.matmul.allow_fp16_reduced_precision_reduction = True` on Ampere+ hosts (sm_8.0+) lets cuBLAS HGEMM use FP16-accumulator tile internals before the FP32 cross-tile reduction. The kernel-vs-reference divergence is ~40% of output elements exceeding the smallest workload's tolerance, with max_abs_error landing at exactly half a FP16 ULP at the failing magnitude. On sm_86 the divergence reliably catches problems with tight per-workload tolerances (e.g. `max_atol=2.9e-5` on the smallest shape); on sm_120 the cuBLAS tile shape sometimes produces results closer to the kernel's so the same kernel may pass 16/16 there despite being structurally vulnerable.
Root Cause: PyTorch's default behavior on Ampere/Blackwell-consumer for FP16 `F.linear` is to use reduced-precision reduction inside cuBLAS HGEMM tiles for throughput. The kernel's pure FP32 accumulator path does not match this precision profile; the rounding direction at near-zero output elements diverges by exactly one FP16 ULP. Trying to fix this by changing the kernel's reduction order (chunked-pairwise vs serial vs Kahan) or by switching to IEEE rsqrt (`__frsqrt_rn`) or to explicit `__fmaf_rn` does NOT help: the divergence is in cuBLAS's tile-internal accumulator dtype, not in any FP32 ordering or fast-math choice on our side.
Solution: Delegate the matmul step to `at::matmul` in the host launcher. The custom CUDA kernel handles only the non-matmul fusion work (e.g. RMSNorm in problem_073's case), writing an FP16 intermediate tensor (matching the reference's `.to(input_dtype)` precision profile per [[match-reference-precision-profile-in-port]]); the host then calls `at::matmul(normalized, weight.transpose(0, 1))` which routes through the SAME cuBLAS HGEMM call PyTorch's `F.linear` uses, with the SAME `allow_fp16_reduced_precision_reduction` setting active. Reshape the matmul output and `copy_()` into the pre-allocated DPS destination tensors. The cost is two kernel launches instead of one fused kernel; local `speedup_factor` typically drops by ~1.5-3x but stays > 1 because RMSNorm dominates over the small-shape matmul. Diagnostic-only `speedup_factor < 1` is acceptable per CLAUDE.md.
Constraints: Applies only when the kernel's matmul step has FP16 inputs AND outputs (the case where cuBLAS reduced-precision reduction kicks in). For FP32 / BF16 matmuls the precision profile is different and this delegation may not be the right call. Also applies only when the kernel does NOT fuse the matmul with subsequent ops that prevent splitting (e.g. softmax fused with attention QK^T); for those kernels you must implement the reduced-precision tile reduction in the inline kernel. To verify the divergence cause empirically: run the reference with `torch.backends.cuda.matmul.allow_fp16_reduced_precision_reduction = True` vs `= False` and quantify the difference in output; if the magnitude matches the kernel's reported error pattern, the delegation fix applies.
Validation Evidence: `baselines/L1/problem_073_fused_encoder_final_norm_to_decoder_cross_attention_kv_projection/cuda_cpp/{main.cpp,kernel.cu,kernel.h}` (R11): before the fix, 15/16 workloads PASSED on sm_86 with workload_index=13 INCORRECT_NUMERICAL at max_abs_error=0.001953125 (=2^-9); after refactoring kernel.cu to RMSNorm-only and delegating the K/V projection matmuls to `at::matmul` in main.cpp, 16/16 workloads PASSED on sm_86. The other 4 R19-R23 pilot ports (problem_006, _040, _066, _087) continued to pass unaltered. Empirical confirmation of reduced-precision divergence: `.humanize/rlcr/2026-05-28_14-00-22/r11_harvest/precision_diff.py` shows `torch.backends.cuda.matmul.allow_fp16_reduced_precision_reduction = True` vs `= False` on this kernel's inputs produces max_abs = 0.0625 and 6806 of 16768 elements differ by > 0.0019 — matching the kernel-vs-reference signature exactly.
Source Rounds: R10 (problem_073 quarantined under typed reason `correctness_workload_quarantine_fp16_precision_drift` — at this point we still believed the [[match-reference-precision-profile-in-port]] fix from R20 covered the failure); R11 (root-caused via empirical precision-toggle diff, fixed via at::matmul delegation, bitlesson recorded).

## Lesson: sol-execbench-correctness-proof-needs-minimal-timing-config
Lesson ID: BL-20260529-sol-execbench-correctness-minimal-timing-config
Scope: scripts/baselines_harness/run.py + native_dispatch.run + any sol-execbench correctness run over a high-workload-count problem (FlashInfer-Bench trace problems carry 36-48+ workloads)
Problem Description: Running a multi-workload problem (e.g. problem_012 GQA paged decode, 48 workloads) through the native sol-execbench evaluator for a CORRECTNESS verdict times out under defaults. The CLI's evaluation subprocess `--timeout` defaults to 600s, but the default timing methodology (warmup_runs=10 + iterations=50, run for BOTH the solution AND the reference, x48 workloads, with an L2 flush between iterations) exceeds 600s. Symptom: stderr shows `Compilation succeeded` then `Evaluating 48 workload(s)...` then `subprocess.TimeoutExpired ... timed out after 600 seconds`; zero JSONL traces emitted; returncode 1. Easy to misread as a kernel bug or a trace-data resolution failure when it is purely a timing-budget timeout.
Root Cause: sol-execbench always runs timing alongside correctness; the correctness verdict is a separate trial but the timing iterations dominate wall-clock. The default BenchmarkConfig (warmup_runs=10, iterations=50, benchmark_reference=true) multiplied by a high workload count blows the default 600s eval `--timeout`.
Solution: For a correctness-only proof, pass a minimal-timing config via `--config <json>` with `{"warmup_runs": 1, "iterations": 3, "benchmark_reference": false, "lock_clocks": false}`. `benchmark_reference=false` skips timing the REFERENCE (the reference is still computed once for the correctness comparison, so the PASSED verdict is unaffected); reduced warmup/iterations cut the solution's timing cost. Also raise the CLI `--timeout` (e.g. 2400) for headroom. Diagnostic timing (speedup_factor) is NOT the point of a correctness gate, so reduced iterations are appropriate — record in the evidence that timing was reduced so the run is never mistaken for a performance measurement. NEVER pass `--lock-clocks` and keep `lock_clocks=false` (CLAUDE.md Rule 2). Result: problem_012 went from a 600s timeout (0 traces) to 48/48 workloads PASSED.
Constraints: Applies to correctness verification (AC-3 / AC-5 / AC-6 gates), NOT to performance / SOL-score measurement (which needs the full timing methodology and is a Phase-2 online-judge concern). The same recipe is the template for the remaining 8 trace-dependent FlashInfer-Bench problems (012-019) and any high-workload-count L1/L2 problem.
Validation Evidence: `.humanize/rlcr/2026-05-29_02-41-41/r1_harvest/run_problem_012_proof.py` + `scripts/baselines_harness/calibration/cache_prediction/problem_012_flashinfer_trace_smoke_v1.toml` (48/48 PASSED with warmup=1 / iterations=3 / benchmark_reference=false after a 600s-timeout under defaults) + `scripts/baselines_harness/tests/test_problem_012_flashinfer_trace_smoke_v1.py`. sm86-coverage-loop R1.
Source Rounds: sm86-coverage-loop R1 (AC-3: 600s eval-timeout diagnosed on the full 48-workload timing run, fixed via a minimal-timing correctness config).

Lesson ID: BL-20260529-conform-gencode-without-rebundle-on-same-arch
Scope: AC-5 bulk-port conformance — baselines/<cat>/<slug>/<lang>/solution.json + the existing <slug>__<lang>__sm86/ evidence bundles + scripts/baselines_scaffold/scaffold.py + scripts/baselines_harness/calibration/sm86_port_done_bar.py
Problem Description: The AC-4 DONE bar requires an explicit `-gencode arch=compute_86,code=sm_86` cuda_cflag, but existing ports were scaffolded with LOCAL auto-detect (no gencode). The naive way to conform an existing, already-profiled port is to add the gencode AND re-run the full surfaces CLI to re-emit the five-surface bundle. For the R18-R30 pilot seed cells that re-emission is actively harmful: four committed tests (test_sm86_pilot_correctness_bundles_v1 / _ncu_3run_v1 / _tier2_v1 / _label_ledger_v1) SHA-pin the existing bundle sub-artifacts, so regenerating the bundle changes those SHAs and turns the frozen pilot tests RED. Re-emitting is also wasted GPU: on the same arch the bundle was originally profiled on, the explicit gencode is a byte-identical no-op.
Root Cause: On an sm_86 host, `nvcc -O3 -gencode arch=compute_86,code=sm_86` and `nvcc -O3` (LOCAL auto-detect -> sm_86) produce identical SASS, so the existing bundle (profiled from the auto-detect build) is already representative of the gencode'd solution. The DONE-bar validator checks the solution's gencode + the manifest's evidence_label/surfaces/host.kind independently; it does NOT require the manifest's `cache_identity.solution_source_hash` to match the live solution, so a byte-identical re-build need not be re-bundled.
Solution: Conform via a structured, idempotent helper (`conform_existing_solution_to_local_sm86`): load solution.json, set `target_hardware=["LOCAL"]`, append the gencode to cuda_cflags if absent, re-validate against the live Solution schema, write back. Do NOT re-emit the bundle. RE-RUN correctness (run.py) on the conformed cell to prove the gencode'd build still compiles + passes (4/4 seed cells: 16/16 PASSED), recording the result in a committed evidence TOML. Then REGENERATE the coverage ledger from disk — the DONE-bar verdict flips to done=True for the now-conformed clean cells while the frozen pilot bundles (and their SHA-pinning tests) are untouched. Teach the scaffold to emit the gencode for NEW ports (`--local-sm86`) so future ports are born conforming. This conform-don't-rebundle path applies whenever the existing bundle was profiled on the SAME arch you are conforming to; a NEW port (no bundle) or a cross-arch conformance still needs a fresh five-surface bundle.
Constraints: Same-arch only — the byte-identity argument fails across arches (sm_86 bundle is not valid for an sm_100a gencode). A cell whose existing bundle has a FAILED surface (e.g. problem_006's nvbit_metrics) still cannot reach DONE by conformance alone (a failed surface is disqualifying regardless of the gencode); it stays not-DONE until the surface is re-run cleanly. Verify the pilot-SHA tests stay green after conforming (they validate bundle sub-artifacts, not solution.json, so adding the gencode to solution.json leaves them green — confirm empirically before relying on it).
Validation Evidence: `scripts/baselines_scaffold/scaffold.py::conform_existing_solution_to_local_sm86` + `scripts/baselines_harness/calibration/cache_prediction/sm86_ac5_batch1_rerun_v1.toml` (040/066/073/087 each 16/16 PASSED with the gencode'd build); `sm86_coverage_ledger_v1.toml` (done_count=4 after conformance); the four `test_sm86_pilot_*` tests + `test_sm86_pilot_seed_frozen_v1` stayed green (216 passed) post-conformance. sm86-coverage-loop R4.
Source Rounds: sm86-coverage-loop R4 (AC-5 first batch; conform-don't-rebundle established to take the 4 clean seed cells to DONE without disturbing the frozen pilot artifacts).

## Lesson: invalid-reference-oom-is-host-capacity-deferral-not-kernel-defect
Lesson ID: BL-20260529-invalid-reference-oom-is-host-capacity-deferral
Scope: AC-5 bulk-port correctness via scripts/baselines_harness/run.py on the RTX 3090 Ti (24 GiB) — large-shape (big batch×seq, large KV-cache-capacity) L1/L2 ports: *_backward kernels whose fixed PyTorch reference materialises large intermediates, AND large-input cells (attention-backward, KV-cache) whose harness input tensors or timing buffers exceed 24 GiB.
Problem Description: A ported cell passes sol-execbench correctness on most workloads but the largest-shape workload(s) FAIL — with status `INVALID_REFERENCE` OR `RUNTIME_ERROR` — so the cell cannot reach the all-workloads-PASS DONE bar. Easy to misclassify as a kernel correctness failure (→ wrongly fix the kernel) or as an sm_86 portability/compile blocker (→ wrongly move to the AC-1 exclusion set). The host-capacity OOM has THREE distinct phases, two of which surface as `RUNTIME_ERROR` (not `INVALID_REFERENCE`).
Root Cause: A host-capacity (24 GiB) `torch.OutOfMemoryError` can fire at three phases, each with a different sol-execbench status: (1) `INVALID_REFERENCE` (`eval_driver.py:470`) when the REFERENCE `run()` itself raises — the fixed reference allocates an intermediate that exceeds 24 GiB (problem_013 backward: `grad_normalized * normalized` at batch=64/seq=8192 ≈ 5 GiB). (2) `RUNTIME_ERROR` with `"gen_inputs failed: CUDA out of memory"` — the harness INPUT-GENERATION phase (before any run()) cannot allocate the workload's input set (problem_060 attention-backward at batch=1/4096×4096 needs >24 GiB of inputs). (3) `RUNTIME_ERROR` with `"Timing failed: CUDA out of memory"` — the inputs fit (~20 GiB, e.g. a batch=8 KV-cache-capacity tensor) but the TIMING phase's additional allocation (fresh-allocator input duplication / buffers) pushes past 24 GiB, even under the minimal-timing config (problem_018). In all three, the failure is host-capacity, NOT a kernel numerical error (`INCORRECT_NUMERICAL`) and NOT an sm_86 compile/codegen defect (the kernel compiles + passes the smaller workloads).
Solution: Classify the cell as a typed `deferred_correctness` coverage-ledger row with a concrete reason naming (a) the failing workload's axes, (b) the status + phase — read the per-workload `evaluation.log` (the CLI `--json` JSONL carries it under `evaluation.log`; run.py's distilled `trace.json` rows do NOT) to confirm the message is a CUDA-OOM string (`gen_inputs failed: ...out of memory` / `Timing failed: ...out of memory` / `Reference run() failed: ...out of memory`), (c) the allocation size vs the 24 GiB host, (d) the pass count (e.g. 15/16, 11/13), (e) that it is expected to fit on B200 (192 GB), (f) that it STAYS IN-SCOPE — NOT an AC-1 exclusion (reserved for fp8/nvfp4 precision-contract problems; a host-capacity limit is not a feature incompatibility). Do NOT modify the reference or drop the workload (the DONE bar requires every workload PASS). CRITICAL: a `RUNTIME_ERROR` is only a host-capacity deferral if the log is an OOM string — a `RUNTIME_ERROR` with "illegal memory access" / "an illegal instruction" / launch-config failure is a GENUINE kernel bug to FIX, not defer. Always read the actual exception; distinguish OOM (host-capacity, defer) from a kernel bug or an INCORRECT_NUMERICAL precision error (fix via [[match-reference-precision-profile-in-port]] / [[delegate-matmul-to-at-matmul-for-reference-hgemm-precision-parity]]).
Constraints: The deferral is host-specific — the same cell may reach DONE on a larger-VRAM host or on B200. The pattern recurs for other large-shape backward L1/L2 cells on 24 GiB; each is its own ledger row, recorded in `deferred.json` at AC-9. A LARGE fraction of cells hitting this would signal the host is too small for the corpus, not a per-cell defect.
Validation Evidence: `scripts/baselines_harness/calibration/cache_prediction/sm86_bulk_correctness_v1.toml` carries 3 deferred_correctness rows — problem_013_fused_residual_rms_norm_backward (R6, INVALID_REFERENCE / reference-run OOM, 15/16), problem_060_fused_attention_qk_matmul_scale_mask_softmax_backward (R10, RUNTIME_ERROR / `gen_inputs failed: CUDA out of memory` at batch=1/4096×4096, 15/16), problem_018_fused_rope_with_qk_norm_and_kv_cache_update (R10, RUNTIME_ERROR / `Timing failed: CUDA out of memory` at batch=8 KV-cache, 11/13) — each with the captured CLI `--json` OOM log in `.humanize/rlcr/2026-05-29_02-41-41/{r6_harvest/problem_013_cli.jsonl, r10_harvest/probe_060.json, r10_harvest/probe_018.json}`. All three regenerate as deferred rows in `sm86_coverage_ledger_v1.toml` (3 deferred / 4 not-done).
Source Rounds: sm86-coverage-loop R6 (first INVALID_REFERENCE / reference-run OOM; diagnosed + classified deferred_correctness in-scope); R10 (the two RUNTIME_ERROR OOM phases — gen_inputs OOM and timing OOM — diagnosed via the CLI --json `evaluation.log`, confirming the host-capacity class is broader than reference-run OOM).

## Lesson: triage-fanout-before-ac5-batch-selection
Lesson ID: BL-20260529-triage-fanout-before-ac5-batch-selection
Scope: AC-5 bulk-port batch selection — choosing which existing baselines/<cat>/<slug>/<lang>/ ports to run through the conform→correctness→bundle pipeline each round (scripts/baselines_harness/run.py + surfaces/cli.py).
Problem Description: Slug names overstate precision-risk. Names like attention_qk_matmul / qkv_projection / output_projection / fused_linear suggest a kernel computes an FP16 matmul in-kernel (the [[delegate-matmul-to-at-matmul-for-reference-hgemm-precision-parity]] precision-risk class), tempting a round to DEFER the whole "matmul/attention/projection cohort" to a special future batch. Acting on the name alone wastes rounds: it pre-defers cells that actually pass cleanly, or sequences the batch poorly.
Root Cause: The existing L1 SOL-ExecBench ports overwhelmingly do NOT compute FP16 matmuls in-kernel. Many delegate the matmul to at::matmul / at::linear in the host main.cpp (kernel.cu is a bare #include stub); the ones that do run an in-kernel GEMM use bfloat16 (or fp32) inputs with FP32 accumulation on the CUTLASS Sm80 TensorOp path — which matches PyTorch's cuBLAS precision profile, so the FP16-reduced-precision divergence does not apply. Only a custom FP16 in-kernel contraction is genuinely precision-risk.
Solution: Run a read-only triage fan-out (one agent per candidate cell) BEFORE batch selection. Each agent opens solution.json + the actual .cu/.cpp sources + the reference spec and classifies: clean (no in-kernel FP16 matmul: elementwise/norm/rope/activation/softmax/reduction, OR matmul delegated to ATen, OR bf16/fp32 GEMM) vs matmul_precision_risk (custom FP16 in-kernel contraction) vs oom_risk (large-shape backward materialising a multi-GiB reference intermediate). Select the round's B≈8-12 from the clean cohort; queue only the genuinely precision-risk / oom-risk cells. Run the triage agents in parallel (read-only, no GPU contention); run the conform→correctness→bundle pipeline serially (single GPU).
Constraints: The classification is a PREDICTION; a cell is DONE only after the actual sol-execbench correctness run passes every workload. oom_risk cells must still be confirmed (INVALID_REFERENCE) before deferring per [[invalid-reference-oom-is-host-capacity-deferral]]. The "clean per triage" verdict held 12/12 in R7, but a future cohort containing a genuine custom FP16 matmul will need the precision fixes; do not treat triage-clean as a license to skip the correctness gate. Borderline-memory "clean" cells (e.g. a ~16 GiB KV-cache cell on a 24 GiB host) should still be held out of a high-throughput batch until confirmed.
Validation Evidence: sm86-coverage-loop R7 — a 37-cell read-only triage fan-out classified 36 clean / 1 oom_risk / 0 matmul_precision_risk; the selected 12 pure-non-matmul cells then passed sol-execbench correctness (16/16, or 12/12 for the two 12-workload cells) and emitted Profiled-local-sm_86 bundles (.humanize/rlcr/2026-05-29_02-41-41/r7_harvest/triage_results.json + batch_summary.json). Coverage ledger done_count 15→27; full-sweep failing set byte-identical to clean HEAD (24 failed / 3947 passed). R8 CONFIRMED the prediction for the most-doubted sub-class: the 12 R7-triage "ATen-delegated bf16" cells (attention output/value/qkv-projection, qk-matmul, score×value matmul, gate-up-swiglu, moe-routing-backward — all `matmul_delegated_to_aten=true`) all passed 16/16 with zero precision failures, because a host `at::matmul`/`at::linear` is the SAME cuBLAS call the reference uses (bit-compatible). Two rounds, 24/24 triage-clean cells DONE; coverage 27→39. The lesson's "delegated/bf16-GEMM ≠ precision-risk" claim is now empirically validated, not just predicted. R9 then CLOSED the lesson's one remaining hedge — the "TF32 watch" on the in-kernel-GEMM sub-class: the 5 in-kernel CUTLASS-GEMM cells (022 fp32, 030 bf16, 035/036/080 fp32; the GEMM is computed in-kernel, not delegated) all passed 16/16 with NO TF32-vs-FP32 divergence, because the ports use FP32 accumulation and the sol-execbench reference matmul agrees within tolerance on sm_86. So both the delegated AND the in-kernel-GEMM sub-classes are validated; across R7+R8+R9 the triage-clean prediction held 34/34, coverage 15→49.
Source Rounds: sm86-coverage-loop R7 (triage fan-out introduced as the AC-5 batch-selection front-end); R8 (the ATen-delegated bf16 cohort prediction confirmed 12/12); R9 (the in-kernel-GEMM / TF32 sub-class confirmed 10/10, closing the TF32 hedge).

## Lesson: cross-check-already-represented-cells-when-enumerating-a-new-category
