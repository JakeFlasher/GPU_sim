Core architectural conflict
---------------------------
The branches are not simple additive changes. They modify the same Rust
modules in different ways:

SM86 branch (A) adds card-backed/effective SM86 behavior:
* `sim/mem/src/l1.rs`: optional set/way/index scenarios (`L1SetIndex`), richer
  static-client merge/hit/sector counters, fixed-register/readiness observers,
  and SM86 L1 cache state arms.
* `sim/mem/src/l2.rs`: SM86 operation/client/packet counters, DRAM demand and
  dirty-tail fields.
* `sim/sm/src/issue.rs`, `issue/candidates.rs`, `issue/config.rs`,
  `issue/readiness.rs`: fixed RF/front-end/readiness and memory-admission
  candidate behavior.
* `sim/sm/src/system.rs`: SM86 carded DRAM service-rate and pressure/route
  observers, plus store/fence completion candidates.
* `sim/sm/src/metrics.rs`, `sim/direct_run/src/{emit,metrics,lib}.rs`:
  extensive SM86 NCU-shaped metric projections and report fields.
* `sim/trace/src/reader.rs`: sector/address/coalescing projections needed for
  SM86 controls.
* `tools/sm120_corpus_replay.py` was generalized to choose `sm_86` or `sm_120`,
  discover SM86 defaults/P-chase card, pass an optional DRAM service rate and
  memory-admission candidate, and permit `--workers 1` or `12`.

SM120 branch (B) adds newer effective SM120 behavior:
* `sim/mem/src/l1.rs`: bounded `L1RequestMaskAudit`, client-indexed request and
  merge-mask histograms, and observer-only static request-mask provenance.
* `sim/mem/src/access.rs`/`cache_op.rs`: explicit async/Blackwell access and
  cache-op classification.
* `sim/trace/src/async_sidecars.rs`, `obligations.rs`, and `reader.rs`:
  TMA generation/coordinate/source relations, shared-bank and local-sector
  projections, and typed sidecar validation.
* `sim/sm/src/replay.rs`, `system.rs`, `issue.rs`, `metrics.rs`, and
  `program.rs`: TMA shadow L2 demand, SM120 memory-role/service arms, effective
  L1/L2/DRAM observers, and the latest conditional active-IPC model.
* `arch_profiles/cards/sm_120-rtx-5090.json` changes DRAM from a typed gap to an
  explicit prototype (`1792000000000 B/s`, 2407 MHz SM, 14000 MHz memory) while
  retaining provenance that this is not a measured service rate.
* CLI removes legacy `--sm120-alpha` and `--ncu-shaped-metrics` switches but
  preserves their internal fields as false/always-emitted behavior; the
  replay runner defaults carded DRAM on and allows workers 1 or 12.

Representative conflicting snippets
------------------------------------
1) `sim/direct_run/src/main.rs`, same common base:

A / SM86 adds an explicit DRAM rate argument:

    [--carded-dram] \\
    [--dram-service-rate-bytes-per-sec N] \\
    [--dirty-writeback-capacity-sectors N]

    let mut carded_dram_bandwidth = false;
    let mut dram_service_rate_bytes_per_sec = None;
    ...
    value if value == OsStr::new("--dram-service-rate-bytes-per-sec") => {
        let raw = take_value(&mut args, "--dram-service-rate-bytes-per-sec")?;
        let rate = raw.parse::<u64>()...;
        if rate == 0 { return Err(...); }
        dram_service_rate_bytes_per_sec = Some(rate);
    }

B / SM120 removes legacy switches:

    [--fast-frontier-only] \\
    [--sm120-effective-l1 ...] \\
    [--sm120-effective-l2 ...] \\
    [--latent-envelope] \\
    ...

    // `--sm120-alpha` and `--ncu-shaped-metrics` are no longer parsed;
    // RunConfig receives `ncu_shaped_metrics: false` and `sm120_alpha: false`.

Question: should the unified CLI retain both legacy switches as hidden aliases
for old SM120 artifacts, or remove them and make architecture-specific behavior
purely card/target driven? How should `--carded-dram` and the explicit SM86
service-rate override interact with SM120's prototype card default?

2) `sim/mem/src/l1.rs` configuration conflict:

A adds physical-sensitivity scenario fields:

    pub set_count: Option<u32>,
    pub ways: Option<u32>,
    pub set_index: L1SetIndex,

    pub enum L1SetIndex {
        FullyAssociative,
        Modulo,
        XorFold,
        ModuloXorFallback,
    }

B adds a bounded observer audit to the same structs:

    #[derive(Debug, Clone, Copy, Default, PartialEq, Eq, Serialize)]
    pub struct L1RequestMaskAudit {
        pub request_count: [u64; 5],
        pub request_line_count: [u64; 5],
        pub request_masks: [[u64; 16]; 5],
        pub same_request_merge_masks: [[u64; 16]; 5],
        pub older_pending_merge_masks: [[u64; 16]; 5],
        pub request_mask_overflow: [u64; 5],
    }

Question: keep both as independent configuration/state and diagnostic layers,
or refactor into a single `L1Geometry`/`L1Observer` abstraction? Which fields
must remain timing-neutral so that SM120 mask audits cannot alter SM86 cache
replacement or timing?

3) Metric projection conflict:

A's SM86 `sim/direct_run/src/metrics.rs` grows SM86-specific counter rows for
constant-client, L0C/L1TEX/L2/DRAM, store-fence and readiness residuals. B's
same file grows SM120 TMA/active-IPC/L1/L2 observer rows and changes row
selection/defaults. Existing output consumers in `final_results/*` expect stable
JSONL schemas.

Question: should the unified output schema namespace rows by `arch_id` (for
example `sm86_*` and `sm120_*`) while preserving old names as aliases, or should
one common row name carry an `arch_scope`/`status` field? Give a backward
compatibility policy for old `3090ti/*.jsonl.zst` and `5090/*.jsonl.zst`.

4) Trace reader conflict:

A adds SM86 sector-plan/coalescing and local/global address validation. B adds
SM120 TMA coordinate/sidecar relationships and shared-bank ideal-vs-observed
wavefront projections. Both extend `ValidatedWarp` and `ValidatedMemoryInstruction`.

Question: what is the safest merge ordering and invariant set? In particular,
which validation failures should be fatal for native traces, which should be
recorded as typed unavailable diagnostics, and how can SM86 traces without TMA
sidecars remain byte/behavior compatible?

5) Replay-runner defaults conflict:

A's generalized runner chooses defaults from the architecture card, uses the
SM86 P-chase card and optional store/fence candidate, and defaults SM86 carded
DRAM/service hypotheses. B's runner targets SM120, defaults carded DRAM on, and
requires the standard full corpus worker policy (12, with sequential 1 now
allowed for timing baselines).

Question: design a single runner contract such as
`--target-arch auto|sm_86|sm_120`, architecture-specific default cards, explicit
`--no-carded-dram`, `--memory-mode`, and corpus-root validation. How should
capture roots be discovered and how should mixed-architecture corpus runs be
prevented?

6) Architecture-card semantics:

A retains SM86 measured/card-backed L1/L2/P-chase values and typed candidates.
B changes only SM120 `dram_bandwidth` from a typed research gap to an
unvalidated prototype hypothesis. The two `sm_120-rtx-5090.json` files differ
only in that block (plus documentation wording).

Question: retain the SM120 prototype as opt-in for scientific conservatism, or
keep B's default-enabled prototype while clearly recording `validated=false`?
How should card loading reject a mismatched SKU/arch and avoid silently using
SM86 facts for SM120 gaps?
