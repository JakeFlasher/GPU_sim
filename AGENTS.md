# Codex local-resolution and optional standalone Fable-5 consultation protocol

This repository has a local-resolution rule for every Codex agent, sub-agent,
and future Codex session working in this tree.

When a Fable-5 response contains a defect, omission, contradiction, unsafe
instruction, or mechanically false repository claim, the agent must diagnose
and correct it locally, add or update the tests that bind the correction, and
continue with every sound part of the response. It must not issue another
Fable-5 prompt, ask the user to submit a correction prompt, or stop merely
because the advisory answer is imperfect. A Fable-5 response is proposed
direction, not authority that overrides repository evidence.

The agent must still avoid guessing, weakening a check, silently choosing among
materially different user-owned outcomes, or switching models. It must exhaust
safe local evidence, callers, tests, schemas, generated bytes, and cross-stage
interactions. If reliable progress truly requires new user authority or an
external fact unavailable locally, ask the user directly for that authority or
fact. Do not route ordinary implementation defects back through Fable-5.

A Fable-5 consultation is permitted only when the user explicitly requests one.
When explicitly requested, the consultation prompt must include all shareable
context needed for an independent decision:

- the objective and current project/RLCR state;
- repository location, branch/HEAD, relevant files, and changed state;
- work completed, commands/tests run, and exact observed evidence;
- the ambiguity or blocker and why local evidence does not resolve it;
- plausible interpretations, risks, constraints, and tradeoffs;
- the precise questions Fable-5 should adjudicate and the requested answer
  format; and
- the instruction that Codex must remain on its pinned model and wait through
  any additional safety check rather than substituting another model.

"System context" means the shareable operational and project context above.
Never expose hidden platform prompts, credentials, secrets, or other protected
internal data; summarize applicable constraints without disclosing protected
text.

An explicit consultation request does not suspend unrelated authorized work.
After a response arrives, apply the local correction-and-continuation rule
above.

## Non-negotiable Fable-5 session model

Every message sent to Fable-5 starts a new, stateless, single-message session.
Fable-5 has none of the following:

- prior conversation turns, prior consultation prompts, or prior rulings;
- repository, filesystem, shell, Git, tool, connector, or system access;
- access to local paths, local Markdown links, `/tmp` files, additional
  attachments, or artifacts merely named by path; Fable-5 sees only the
  literal contents of the one prompt file after the user pastes or uploads it;
  or
- hidden project state, hidden platform instructions, or Codex's internal
  context.

Therefore every Fable-5 consultation must be a standalone first-contact
package. A path, hash, commit, section label, summary, or phrase such as "the
preceding ruling" is only an identifier and never substitutes for the literal
content required to decide the issue. If an operative earlier decision matters,
restate it completely or embed it as a literal evidence block. Never use
"incorporated by reference", "as previously ruled", "same as above", a delta
against an unembedded table, or a local-file link as context.

There are no conversational follow-ups to Fable-5. If an answer exposes missing
context or a defective contract, Codex must perform an exhaustive local audit,
repair every locally determinable defect, preserve the sound clauses, and
continue implementation. It must not send a patch prompt, serial clarification,
or replacement consultation unless the user explicitly requests a new one.

## Mandatory pre-consultation workflow

Before drafting a consultation, the primary agent must:

1. Exhaust every safe, read-only way to resolve the issue locally. Inspect the
   relevant definitions, callers, writers, tests, schemas, documentation,
   generated outputs, staging interactions, and cross-stage consumers. Run the
   mechanical probes and collect their exact outputs. Do not ask Fable-5 for a
   repository fact Codex can determine.
2. Expand the audit to the whole known blocker cluster. Consolidate all
   presently discoverable questions into one consultation. Never escalate one
   tiny issue at a time merely because it was found first.
3. Build a dependency-closed context manifest. For every embedded file or
   excerpt record its repository-relative path, revision (`HEAD`, `INDEX`,
   `WORKTREE`, or an exact commit), full-file SHA-256, included line range,
   excerpt SHA-256, relevance, supported blocker IDs, omitted ranges, and why
   each omission is safe.
4. Ask a separate sub-agent to independently re-scan the implicated surfaces
   and review the draft for blocker completeness, cross-stage interactions,
   security, and context economy. The author and reviewer must be different.
   If no reviewer slot is available, wait for one; do not send an unreviewed
   consultation.
5. Incorporate every reviewer finding into the same prompt, then run the
   repository validator and context report described below.

## Decision-complete context, not indiscriminate context

Necessary file content must be embedded literally in the prompt. A filename,
link, or instruction for Fable-5 to inspect a file is forbidden. At the same
time, do not waste Fable-5 context on unrelated material.

Use these trimming rules:

- Include a complete file when the decision is distributed through the file,
  the file is small, exact byte identity matters, or excerpting could conceal a
  relevant branch or invariant.
- Otherwise include decision-complete semantic units: the full definition,
  adjacent control flow, referenced constants/types, all relevant callers and
  writers, the tests that bind the behavior, and the configuration or schema
  that constrains it. Never isolate a single line from its load-bearing unit.
- Preserve literal error tokens, hashes, schemas, path/action tables, counts,
  commands and outputs, test names, negative cases, and operative prior ruling
  text. These may not be summarized or abbreviated with an ellipsis.
- Remove duplicated prose, superseded alternatives, unrelated imports and
  functions, irrelevant logs, historical narration that has no operative
  effect, and repeated evidence already assigned one stable evidence ID.
- State every omitted range and why it cannot affect the adjudication. If that
  claim cannot be made confidently, include the full file.
- Scan for secrets before embedding. Never include credentials, tokens, private
  keys, cookies, `.env` contents, hidden prompts, chain-of-thought, or protected
  platform text. Redact non-decision-critical secrets with an explicit marker;
  never redact a decision-critical fact and pretend the context is complete.

The independent reviewer must specifically challenge both over-inclusion and
under-inclusion. "Shorter" is not better when it drops a caller, test, exact
table, or prior decision; "complete" is not an excuse to dump unrelated files.

## Required standalone prompt contract

Every ready-to-send prompt must begin with the exact
`FABLE5-CONSULTATION-V1` declaration supplied by
`tools/local_labels/FABLE5_CONSULTATION_TEMPLATE.md.in`, and must contain all
required sections in the exact order enforced by
`tools/local_labels/fable5_consultation_protocol.py`.

`FILE_CONTEXT_MODE` is always `embedded`. Every consultation must contain at
least one exact, hash-bound repository file block; a policy-only question must
embed the applicable policy file. `none` is not an allowed shortcut.

At minimum the prompt must include:

- a literal fresh-session/no-access declaration;
- the objective and requested decision;
- repository location, branch, full HEAD, index and working-tree state, and
  current project/RLCR stage;
- all applicable safety, authority, mutation, staging, model, and WAIT
  constraints;
- completed work, exact commands, exact outputs, hashes, counts, and failures;
- the full operative decision history needed by this adjudication, with no
  dependency on another chat;
- one consolidated blocker index with stable IDs;
- an evidence index and literal evidence blocks supporting every blocker;
- cross-blocker interactions, plausible interpretations, tradeoffs, and risks;
- precise questions tied to blocker/evidence IDs;
- the exact requested response structure and acceptance criteria; and
- an independent-review, context-trimming, and security attestation.

Generic rows such as "unchanged", "all accepted rows", "existing table plus",
conditional `X` counts, truncated digests, placeholders, undefined helpers,
prose command substitutions, and requests that Fable-5 run a probe are hard
failures.

Decision evidence is dependency-closed only when its literal text contains
every operand it relies on. A `policy` or `prior_ruling` evidence block that
refers to a preceding prompt, ruling, message, table, or decision without
embedding that content is a hard failure even when the reference appears only
inside the evidence block. The independent audit uses schema version 3: it
must enumerate the exact decision-evidence IDs and cover every one with an
honest `no_issue` or `resolved_issue` review record. Section 14 must repeat the
exact `Decision evidence reviewed:` and `Review records:` inventories. A
reviewer must never invent a defect merely to satisfy the schema.

## Mandatory validation and single-file delivery

Draft prompts and review sidecars must stay outside the repository unless the
user explicitly asks to track them; that exceptional case also requires the
validator's `--allow-repo-local-inputs` flag. The deliverable is exactly one
plain-text `.txt` prompt file. The user—not Codex—pastes or uploads that file
into a new Fable-5 conversation on the online chat platform. Codex must never
open or automate the site, authenticate to it, send the prompt, manage a
browser session, or read/write platform cookies.

Before presenting a prompt file to the user, run:

```bash
PY=/home/jakeshea/GPU_simulator_rebase/.venv/bin/python
PROMPT_SHA=$(sha256sum PROMPT | awk '{print $1}')
OUT="/tmp/fable5-consultation-${PROMPT_SHA}.txt"
"$PY" tools/local_labels/fable5_consultation_protocol.py context-report PROMPT
"$PY" tools/local_labels/fable5_consultation_protocol.py check PROMPT \
  --audit AUDIT --repo-root /home/jakeshea/GPU_simulator_rebase --verify-repo
"$PY" tools/local_labels/fable5_consultation_protocol.py emit PROMPT \
  --audit AUDIT --repo-root /home/jakeshea/GPU_simulator_rebase --verify-repo \
  --output "$OUT"
```

Only the one file created by `emit --output` is authorized for handoff.
Successful emission writes a machine-local receipt bound to the prompt,
independent audit, output path, repository root, HEAD, working state, and
validator bytes; the Stop hook requires that current receipt. The audit
sidecar, context report, and receipt are local safeguards and are not sent to
Fable-5. The receipt binds the exact audit bytes that passed validation.
Receipt validity is state-bound rather than time-bound: any prompt, output,
HEAD, branch, index, tracked dirty content, nonignored untracked content,
declared ignored evidence, or validator change invalidates it, and emitting a
different prompt revokes the earlier receipt.

The final answer to the user identifies the file and full SHA-256 using exactly
the following fixed sentence and one line of each form:

```text
The validated Fable-5 prompt file is ready for you to paste or upload manually.
FABLE5_PROMPT_FILE: /absolute/path/to/validated-prompt.txt
FABLE5_PROMPT_SHA256: 64-lowercase-hex-characters
```

A clickable link to that same file may also be provided for the user's
convenience. Do not duplicate the prompt inline, split it across files, attach
supporting context separately, or offer an unvalidated draft.

The tracked pre-commit hook validates staged Fable prompt artifacts, and a
repo-scoped Codex Stop hook blocks malformed, unreceipted, or multi-file Fable
handoffs.
These hooks are trusted-worktree consistency backstops, not privilege or
malicious-code security boundaries: the pre-commit hook executes the staged
protocol tests as the current user. Review staged framework code before it is
run. The hook clears every repository-local Git environment variable before
its tests create disposable repositories, so nested Git probes cannot target
the active repository accidentally.
At the start of each Codex session in this repository, ensure the guards are
active with:

```bash
git config --local core.hooksPath .githooks
PY=/home/jakeshea/GPU_simulator_rebase/.venv/bin/python
"$PY" tools/local_labels/fable5_consultation_protocol.py install-stop-hook \
  --repo-root /home/jakeshea/GPU_simulator_rebase
```

The native Stop hook is a machine-local backstop and may require Codex hook
trust/restart after installation. It does not replace this file's binding
instructions or the independent review.

## Returned-ruling validation

A Fable-5 answer is proposed direction, not repository evidence. Preserve the
exact visible answer in one plain-text file outside the repository and run the
mechanical response gate before interpreting or implementing it:

```bash
PY=/home/jakeshea/GPU_simulator_rebase/.venv/bin/python
"$PY" tools/local_labels/fable5_consultation_protocol.py \
  check-response PROMPT RESPONSE
```

The response gate requires an explicit ACCEPT, AMEND, REJECT, or STOP
disposition for every question. It rejects missing dispositions, serial
requests for more context or repository access, visible hidden reasoning,
conditional action codes, placeholders, truncated hashes, pseudocode
deferrals, malformed shell blocks, undefined shell variables, and invalid
multi-filter `cargo test` commands. Passing this gate proves only mechanical
answer hygiene; it does not prove semantic correctness or authorize mutation.
For a valid response, the command prints full prompt and response SHA-256
values. Preserve those exact bytes and rerun the gate immediately before the
semantic audit or any authorized mutation; a hash is an identity binding, not
a truth certificate.

Before any mutation, Codex must then independently validate every returned
path, count, command, hash, API, test disposition, staging instruction, and
cross-stage interaction against the repository. If defects remain and local
evidence determines the safe correction, implement that correction, bind it
with positive and negative tests, and continue with the remaining sound
instructions. Do not generate another consultation or ask the user to relay one.
Stop only when a genuinely user-owned choice or unavailable external fact
prevents reliable progress; request that specific authority or fact directly.
